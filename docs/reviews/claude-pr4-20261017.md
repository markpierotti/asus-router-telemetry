## Findings, by impact

**1. Medium: some temporary collector failures stop the service for good.**
- The unit comment says exit 1 means a hard stop, 2 a bad config and 3 a lock conflict, and `RestartPreventExitStatus=1 2 3` stops systemd restarting on any of them (`deploy/slim/etc/systemd/system/rtax-collector.service:12-17`).
- In the code, exit 1 isn't limited to hard stops. `main()` returns 1 for any `TelemetryError` that escapes, and for `BrokenPipeError` (`collector/rtax_telemetry/cli.py:806-813`).
- Exit 3 isn't only "another run holds the lock". Any other `TelemetryError` from `acquire_lock`, such as a storage error, also returns 3 (`cli.py:475-477`).
- So a temporary error outside the loop can stop collection permanently. The "collector stale" alert would notice, but alert delivery is still pending.
- Fix: give hard stops their own exit code and prevent restarts only for that code and bad config. Or at least correct the unit comment, plus `slim-deployment-20261017.md:66-67`, which repeats the claim.

**2. Medium: the "Pi-hole DNS response time" panel uses the wrong metric.**
- `deploy/slim/var/lib/grafana/dashboards/pihole.json` plots `probe_dns_lookup_time_seconds{job="dns_pihole"}`.
- That metric times the probe's lookup of the target's name. The target is an IP address (`prometheus.yml:51`), so the panel shows about zero and never measures Pi-hole's answer time.
- Use `probe_dns_duration_seconds{phase="request"}` or `probe_duration_seconds`. The live dashboard probably has the same problem if this file matches it.

**3. Medium: the publication records are out of date now that CI has passed.**
- `docs/slim-publication-checks.md:19-20,45-46` still says "final hosted CI remains a gate". It should record what you reported: head `b8cf1c1`, four jobs, 388 collector tests with one skip, four exporter tests and the reporter checks.
- The counts agree with each other: the 386 local tests plus the two new parent-sync tests make 388.
- `claude-review-brief.md:5`, `provenance.md:11-12` and `slim-publication-checks.md:41-43` still say the Claude review couldn't run. Update them to say a source-level review happened, within the limits listed below. It isn't approval of hardware behaviour.

**4. Low–medium: the Mac pull script trusts file names sent by Slim.**
- `deploy/slim/macos/pull-slim-backups:10-13` uses names from `list` directly in `$DEST/.$f.part` and `$DEST/$f`.
- If Slim were compromised it could send a name like `../…` and make the Mac write outside `~/Backups/slim`.
- Fix: on the Mac, check each name against the same `slim-YYYYmmdd-HHMMSS.tar.gz` pattern that `slim-backup-serve:10` enforces.

**5. Low: two placeholder and privacy inconsistencies.**
- `collector/config.example.json:3` uses `192.0.2.1` as the target. The deployment table maps that address to the gateway and puts the ASUS at `192.0.2.20` (`deploy/slim/README.md:18-20`), yet setup step 2 tells readers to start from this file. Add a note or use `.20`.
- `slim-rules.yaml:63,105` names the gateway as "TP-Link". Everywhere else the docs say "Main gateway", so this reveals the household's gateway vendor.

**6. Low: the durability wording is broader than the code.**
- `collector/README.md:117` says writes are fsynced at both file and directory level.
- Three cases don't sync the directory: creating a new append log (`store.py:201-216`), moving a corrupt state file aside (`store.py:415`), and deleting pruned samples (`store.py:469,479`).
- The 1.6.1 fix itself is correct. `_atomic_write` now syncs `path.parent` (`store.py:171`), and `test_storage_parent_sync.py:40` would have failed against the old behaviour. Narrow the README claim to match.
